# Runbook Niche Radar

## Запуск и обновление

Первый запуск:

```bash
./bin/setup && docker compose up -d --build
```

Обновление на новую версию кода:

```bash
docker compose down
git pull
docker compose up -d --build
# сервис migrate применит миграции идемпотентно до старта приложения
```

Миграции не запускаются конкурентно: их применяет одноразовый сервис `migrate`
после healthcheck PostgreSQL; app/workers ждут его завершения
(`service_completed_successfully`).

## Порты и доступ

- Приложение слушает `APP_PORT` из `.env` (по умолчанию `127.0.0.1:8080`) — только loopback.
  Если порт занят, укажите свободный, например `APP_PORT=127.0.0.1:8180`.
- PostgreSQL наружу не публикуется.
- Один владелец: вход по паролю, регистрация отключена. REST-токены (read/write) —
  раздел «Настройки»; хранится только хеш токена, отзыв — в один клик.
- Для удалённого доступа владелец самостоятельно настраивает TLS/прокси; в базовой
  поставке публичного доступа нет.

## Резервное копирование

```bash
./bin/backup /absolute/path/backup-dir
```

Что входит:

- дамп PostgreSQL (`pg_dump`, согласованный снимок; на время копирования web/app/workers
  останавливаются, чтобы оригиналы не разъехались с дампом);
- архив `storage/app/originals` (оригиналы CSV по SHA-256) и `exports`;
- `backup-meta_*.env`: версия PostgreSQL, дата, `APP_KEY` (нужен при наличии
  зашифрованных данных).

Гипотезы, ниши, сохранённые поиски и конфигурации — в дампе БД.

## Восстановление

```bash
./bin/restore /absolute/path/backup-dir
```

Требует ввода `YES`: текущая база полностью заменяется, файлы оригиналов
дополняются/заменяются из архива. При необходимости верните `APP_KEY` из
`backup-meta_*.env` в `.env` (секреты восстанавливаются вручную — это осознанное
решение не хранить пароли в копии автоматически).

Проверка после восстановления: `curl -s localhost:8080/api/v1/health` → `"status":"healthy"`.

## Диагностика

| Что проверять | Как |
|---|---|
| Доступность процесса | `curl localhost:8080/api/v1/ping` |
| Готовность БД и heartbeat воркеров | `curl localhost:8080/api/v1/health` |
| Стек | `docker compose ps` |
| Импорт | `docker compose logs worker-import`; прогресс — таблица `import_jobs` |
| Зависшие задания | помечает `niche:check-stale-jobs` (scheduler, каждые 5 минут) |
| Ошибки импорта | `GET /api/v1/imports/{id}/errors` (UI: «Данные» → блок ошибок) |

Импорт можно отменять (`POST /api/v1/imports/{id}/cancel`) и перезапускать
(`POST /api/v1/imports/{id}/retry`): этапы идемпотентны, двойных наблюдений не бывает.

## Очистка

- Временные экспорты удаляются автоматически через 7 дней (`niche:cleanup-exports`,
  scheduler). Оригиналы и гипотезы автоматически не удаляются.
- Удаление отчёта — из UI с подтверждением; при ссылках из гипотез/ниш блокируется
  с перечислением зависимостей.
