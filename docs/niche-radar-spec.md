# Техническое задание: Niche Radar

Персональный инструмент исследования поискового спроса и поиска ниш для онлайн-сервисов.

Версия документа: 1.2 · Дата: 1 октября 2026 года · Целевая версия приложения: 1.0 · Формат: локальное веб-приложение для одного владельца, развёртываемое через Docker Compose.

Изменения редакции 1.2: аутентификация и авторизация полностью убраны — приложение локальное, REST и UI работают без входа и токенов.

Изменения редакции 1.1: проверен реальный образец `Top10.csv`; уточнены имена заголовков, шесть уникальных замеров, допустимые позиции рейтинга и контрольные значения импортера. Полный файл пока не исследован.

## 1. Цель и ожидаемый результат

Создать инструмент, который превращает CSV-отчёты популярных запросов Яндекса в проверяемые гипотезы для разработки онлайн-сервисов.

Основной рабочий цикл:

1. Загрузить отчёт и проверить его структуру и историю замеров.
2. Найти запросы с заметным, устойчивым ростом и признаками задачи, решаемой программным продуктом.
3. Объединить релевантные запросы в нишу, изучить объём наблюдаемого спроса и его динамику.
4. Сохранить продуктовую гипотезу с подтверждающими запросами и заметками.
5. При загрузке следующего отчёта повторить анализ и сравнить изменения.
6. Выполнять те же исследования программно через REST API и через MCP из внешнего ИИ-агента.

Ключевой результат — список обоснованных кандидатов для дальнейшего исследования. Сервис не оценивает достоверно выручку, конкуренцию, платёжеспособность или вероятность успеха продукта: таких данных в исходном отчёте нет.

Продукт рассчитан на личное использование и локальный запуск: аутентификации и авторизации нет, доступ ограничен loopback-портом Docker-хоста. Регистрация, команды, тарифы, биллинг, публичные страницы и многопользовательская изоляция не входят в первую версию.

Docker-образы зафиксировать по конкретным версиям, без `latest`. Для Laravel ориентироваться на поддерживаемую стабильную ветку и её официальные требования к PHP.

## 4. Исходные данные и их смысл

Основание — приложенные `readme.txt` и реальный образец `Top10.csv` из 10 строк данных. Формат образца проверен; подтверждённое сопоставление описано в разделе 4.3. Полный CSV на 3 млн строк пока не предоставлен, поэтому его качество и производительность обработки ещё требуют проверки. Структура импортера должна допускать настройку сопоставления колонок при изменении формата.

Полный отчёт содержит до 3 000 000 строк. Описаны следующие поля:

| Поле источника | Внутреннее представление | Примечание |
|---|---|---|
| `#` | `rank_current` | Текущая позиция по точной частотности |
| `Предыдущий #` | `rank_previous` | `0` означает отсутствие в прошлом рейтинге |
| `Ключевое слово` | `phrase_original` | Сохранять исходную формулировку |
| `Слов` | `source_word_count` | Дополнительно считать собственное число слов |
| `Символов` | `source_char_count` | Дополнительно считать число Unicode-символов |
| `Частотность Весь мир` | `broad_frequency` текущего замера | Широкая частотность |
| `"[!Частотность !Весь !мир]"` | `exact_frequency` текущего замера | Реальный заголовок после CSV-разбора; в README обозначен иначе |
| Колонки с суффиксами `1`, `2`, … | Наблюдения предыдущих/текущего замеров | По README суффикс `1` соответствует последнему замеру |

### 4.1. Обязательные правила интерпретации

- Базовая метрика спроса — точная частотность. Широкую показывать отдельно.
- Не складывать широкие частотности по фразам как объём рынка: они пересекаются.
- Сумму точных частотностей подписывать «суммарная точная частотность выбранных формулировок», без обещания числа людей, клиентов или всего рынка.
- Изменение позиции в рейтинге не заменяет изменение частотности.
- Отсутствие строки в отчёте, пустая ячейка и числовой ноль — разные состояния.
- «Впервые в рейтинге» не означает «впервые возникший спрос».
- Частотность относится к периоду, определённому источником. Дата сканирования не задаёт автоматически длительность этого периода.
- Пока даты сканирований неизвестны, показывать порядковые замеры. Не называть их месяцами, не рассчитывать месячный или годовой темп.
- Несколько близких сканирований могут относиться к перекрывающимся периодам. Устойчивость в них — описательная характеристика, а не доказательство статистической независимости.
- История внутри текущего топа описывает именно фразы, попавшие в текущий отчёт; это не полная история поискового рынка.

### 4.2. Идентичность фраз и замеров

Исходную фразу хранить без изменения. Для идентичности использовать Unicode NFC и удаление краевых пробелов; остальные изменения не должны склеивать строки автоматически. Для поиска создать отдельное поле с приведением регистра и пробелов. Замены `ё/е`, лемматизацию и объединение вариантов применять только как явно выбранный режим поиска или правила ниши.

Рейтинг не является ID фразы. Идентификатор фразы устойчив между импортами.

Каждый отчёт хранит собственный упорядоченный набор замеров. Ненумерованная колонка и колонка с суффиксом `1` по описанию являются двумя представлениями одного последнего замера. Сравнить их значения потоково по всем строкам. При совпадении сохранить одно наблюдение; при расхождении заблокировать публикацию до выбора владельцем основной колонки и сохранить факт расхождения.

Истории разных файлов по умолчанию не склеивать. Совпадение номера колонки или даты загрузки не доказывает, что это один замер. Версия 1.0 поддерживает историю внутри отчёта и явное сравнение двух выбранных отчётов; автоматическая сквозная календарная история не требуется.

### 4.3. Подтверждённый профиль `Top10.csv`

Образец содержит 10 записей данных и строку заголовков; в каждой записи 19 колонок. Размер — 2225 байт, кодировка UTF-8 с BOM, разделитель `;`, символ кавычки `"`, экранирование вложенной кавычки удвоением. Переносы строк в образце — LF; импортёр также должен принимать CRLF. В числах нет разделителей тысяч, все наблюдаемые частотности — неотрицательные целые.

Имена ниже приведены **после стандартного CSV-разбора**. Вложенные кавычки являются частью имени точной частотности. Например, сырой CSV-заголовок `"""[!Частотность !Весь !мир]"""` преобразуется парсером в `"[!Частотность !Весь !мир]"`. Не удалять кавычки глобальной заменой до разбора CSV.

| Номер колонки, начиная с 1 | Заголовок после разбора | Назначение |
|---|---|---|
| 1 | `#` | Текущий ранг |
| 2 | `Предыдущий #` | Предыдущий ранг |
| 3 | `Ключевое слово` | Фраза |
| 4 | `Слов` | Число слов источника |
| 5 | `Символов` | Число символов источника |
| 6 | `Частотность Весь мир` | Дублирует текущую широкую из колонки 12 |
| 7–12 | `Частотность Весь мир 6`, затем `5`, `4`, `3`, `2`, `1` | Шесть широких частотностей от старой к новой согласно нумерации README |
| 13 | `"[!Частотность !Весь !мир]"` | Дублирует текущую точную из колонки 19 |
| 14–19 | `"[!Частотность !Весь !мир]" 6`, затем `5`, `4`, `3`, `2`, `1` | Шесть точных частотностей, сопоставленных с широкими по суффиксу |

В десяти строках равенство колонок 6/12 и 13/19 подтверждено. После удаления этих дублирующих представлений получается **шесть уникальных замеров**, то есть 60 строк `observations`, каждая с парой exact/broad, а не 70 или 120 наблюдений. Внутренние ordinal 1…6 соответствуют исходным суффиксам 6…1; исходный суффикс сохранять в метаданных.

Заголовки распознавать по именам и разрешённым алиасам, а не по жёсткой позиции столбца. Описанное в README имя `Частотность "[!Весь !мир]"` поддержать как отдельный алиас. Не определять вид частотности только по наличию слов «Частотность Весь мир» и не полагаться на порядок столбцов. Неизвестные/неоднозначные заголовки требуют ручного сопоставления.

Позиции образца — 2…11. Начало с 1 и непрерывность рангов не являются условием корректного импорта: файл может быть фрагментом или отфильтрованной выборкой. Не перенумеровывать ранги. В интерфейсе загрузки хранить `coverage_type=unknown|full_top|sample|filtered`, по умолчанию `unknown`; для этого образца — `sample`. Принадлежность к полному топу не выводить из имени файла или максимального ранга. Показывать тип охвата в аналитике и ответах API/MCP.

Текущие точные частотности в образце убывают; исходные длины слов/символов совпадают с вычисленными для всех 10 фраз. В образце нет дат сканирований, определения длительности периода частотности, пропущенных значений и предыдущего ранга `0`. Поэтому порядок замеров задаётся описанием источника, календарные даты остаются неизвестными, а непредставленные граничные случаи проверяются синтетическими fixtures.

Контрольная строка «переводчик»: rank=2, previous_rank=2, broad_current=34635675, exact_current=21466358. Её точная история по времени: `[24704716, 24993362, 25094186, 24831529, 25726636, 21466358]`.

Контрольный пример резкого изменения: точная история «чемпионат мира матчи» — `[1866, 846, 568, 468, 493, 14868825]`. Рост сосредоточен в последнем переходе; `C=2/5=0.4`, поэтому строка не проходит пресет устойчивого роста, несмотря на огромный относительный прирост. Данных недостаточно, чтобы установить причину скачка или назвать его сезонным; требуется проверка дат и источника.

## 5. Пользовательские сценарии и интерфейс

Интерфейс на русском языке, desktop-first, рабочая ширина от 1280 px. На более узком экране основные операции доступны; широкие таблицы допускают горизонтальную прокрутку. Цвет не должен быть единственным обозначением роста, ошибок или статуса. Все фильтры доступны с клавиатуры.

### 5.1. Экран «Данные»

- Список отчётов: название, файл, размер, дата загрузки, заявленная дата источника, число строк, число замеров, статус, предупреждения.
- Загрузка `.csv` до 5 GiB по умолчанию; лимит настраивается согласованно в Nginx, PHP и приложении.
- Предпросмотр первых 100 строк, определение разделителя и формы заголовков, сопоставление полей.
- Настройка последовательности замеров от старого к новому, необязательных дат и периода частотности, если он известен.
- Кнопки «Запустить», «Отменить», «Повторить», «Скачать ошибки», «Сделать активным», «Удалить».
- Прогресс этапа, прочитанные байты, обработанные строки, скорость и время выполнения. Оценку оставшегося времени показывать только после накопления статистики.
- Статус нового отчёта не меняет активный отчёт до успешной публикации и выбора пользователя.

### 5.2. Экран «Исследование»

Основной рабочий экран — серверная таблица результатов.

Фильтры:

- выбранный отчёт и диапазон замеров;
- точная фраза, подстрока, включающие и исключающие слова;
- режим включения: любое из слов / все слова; режим совпадения: целый токен / подстрока;
- точная и широкая частотность: от/до;
- число слов: от/до;
- абсолютный и относительный рост: от/до;
- устойчивость, сохранение относительно пика, число доступных замеров;
- впервые в рейтинге, низкая база, неполная история;
- признаки программной задачи, информационного или навигационного запроса;
- собственные метки, принадлежность нише, включение/исключение сохранённого словаря брендов.

Токен в базовом режиме — непрерывная последовательность Unicode-букв или цифр. Морфологические варианты не должны добавляться скрыто. Поиск подстроки и поиск токена — разные операции.

Колонки: фраза, точная/широкая частотность, текущая позиция, изменение позиции, краткая история, прирост в единицах и процентах, устойчивость, приоритет исследования, объясняющие флаги.

По умолчанию 50 строк на страницу; максимум 200. Серверная сортировка с устойчивым вторичным ключом `keyword_id`. Курсорная пагинация вместо глубокого `OFFSET`. Пустые метрики сортировать в конце. Общее число совпадений можно получать отдельно асинхронно.

Состояние фильтров сохранять в URL и как именованный поиск. Действия: открыть фразу, добавить выбранные строки в нишу, сохранить поиск, экспортировать выборку. Нельзя загружать все 3 млн строк в браузер.

### 5.3. Карточка фразы

- Исходная формулировка, источник, определение частотности и доступная история.
- Графики точной и широкой частотности с раздельными сериями и явной шкалой; пропуски не соединять как реальные значения.
- Формула роста, исходные значения, компоненты приоритета и версия правил.
- Текущий и предыдущий ранг; для предыдущего `0` подпись «не было в прошлом рейтинге».
- Фразы с общими значимыми словами и похожим написанием, с указанием способа поиска.
- Привязанные ниши, заметки и продуктовые гипотезы.

### 5.4. Экран «Кандидаты»

Две вкладки: «Растущие фразы» и «Предложения групп».

В первой — пресеты поиска и объяснимый приоритет из раздела 7. Во второй — группы по повторяющимся значимым словам и соседним парам слов. Они помогают увидеть повторяющуюся задачу за отдельными формулировками и служат заготовками для ручных ниш.

Для группы показывать примеры, размер, долю растущих фраз, точную частотность выбранного состава, динамику и долю лидирующей фразы. Можно исключить шум, изменить название и сохранить как нишу.

### 5.5. Экран «Ниши»

Ниша — сохранённая пользователем подборка фраз с названием и описанием задачи.

Поддержать два режима:

- **Фиксированный список:** пользователь выбирает конкретные фразы.
- **Правило поиска:** набор фильтров плюс ручные включения/исключения; при пересчёте создаётся новая версия состава.

Для обеих форм пересчёт сохраняет неизменяемую версию состава. Результаты прошлой оценки не меняются при добавлении новых фраз.

Приоритет правил состава: `(совпадение с фильтрами ИЛИ ручное включение) И НЕ ручное исключение`. Для фиксированной ниши применяются только ручные списки. Фраза, отсутствующая в выбранном отчёте, остаётся в пользовательском списке, но помечается как не имеющая наблюдения; при агрегировании не заменяется нулём.

Карточка ниши: состав, история, рост, концентрация на лидирующей фразе, доля растущих участников, качество покрытия, связанные гипотезы. Общие фразы в двух нишах допустимы, но общий итог нескольких ниш считать по объединению уникальных фраз.

### 5.6. Экран «Гипотезы»

Поля гипотезы:

- название и связанная ниша;
- целевая аудитория, задача, существующий способ решения;
- идея онлайн-сервиса и минимальная полезная функция;
- предположение о монетизации;
- подтверждающие фразы, выбранный отчёт и сохранённая оценка;
- заметки, ссылки на дальнейшее исследование;
- следующий эксперимент и критерий результата;
- статус: «кандидат», «исследую», «проверяю», «в разработке», «отложено», «отклонено»;
- причина отклонения или откладывания.

Аудитория, монетизация и конкуренция заполняются владельцем или внешним агентом как гипотезы, не выдаются за наблюдаемые данные CSV. В версии 1.0 MCP не изменяет карточки; владелец переносит результаты исследования через UI/API.

### 5.7. Дашборды

Обзор активного отчёта: число фраз, наличие истории, число кандидатов по текущему пресету, лидеры роста и падения, новые участники рейтинга, предупреждения качества.

Для ниши: динамика фиксированного состава, распределение частотности, доля растущих фраз, концентрация, новые и отсутствующие в следующем отчёте фразы. Каждый график открывает соответствующую выборку. Не добавлять декоративные показатели без перехода к исходным строкам.

## 6. Импорт и подготовка данных

### 6.1. Требования к обработке

1. Сохранить оригинал в volume, вычисляя SHA-256 потоково.
2. Создать запись импорта; одинаковый хеш уже принятого файла возвращает существующий отчёт, без дублирования. Разные настройки разбора одного файла оформлять как новую ревизию обработки с явной связью с оригиналом.
3. Поддержать UTF-8 с BOM и без него; разделители `;`, `,`, TAB. Использовать CSV-парсер с поддержкой кавычек и переносов внутри полей. Не разбивать файл простым `split` по переводу строки.
4. Невалидный UTF-8 не исправлять молча. Предложить указать кодировку или загрузить исправленный файл; автоматическое угадывание с потерей символов запрещено.
5. Проверить заголовки, типы, неотрицательность частотностей, уникальность фраз внутри отчёта, порядок и сопоставление замеров.
6. Пустые частотности хранить как `NULL`, нули как `0`; `rank_previous=0` сохранять отдельным признаком отсутствия в предыдущем рейтинге.
7. Текущая точная частотность и непустая фраза обязательны. Дополнительные исторические колонки необязательны. Без достаточной истории доступен поиск, но рейтинг устойчивого роста недоступен.
8. Совпадающие дубликаты строк схлопывать с отчётом о количестве. Конфликтующие дубликаты не суммировать; блокировать публикацию до исправления или явно выбранной политики исключения.
9. Сохранять ошибки по логическому номеру записи CSV, колонке и причине. Режим по умолчанию строгий. Частичную публикацию разрешать только после явного выбора «пропустить ошибочные записи», с сохранением числа исключений и отметкой о неполноте.
10. Загружать данные в промежуточные таблицы пакетами; массовая запись через `COPY FROM STDIN`, без создания Eloquent-модели на каждую строку. `COPY` предназначен для переноса больших объёмов данных. [PostgreSQL COPY](https://www.postgresql.org/docs/current/sql-copy.html).
11. Рассчитать материализованные метрики, токены и группы; обновить статистику планировщика.
12. Перевести отчёт в `ready` только после завершения всех обязательных этапов. Запросы пользователя всегда ограничивать опубликованными отчётами.

Формат текущих и исторических колонок задаётся адаптером `BukvarixCsvAdapter`. Новый формат файла должен добавляться отдельным адаптером, без изменений расчётов и интерфейса.

### 6.2. Состояния и восстановление

Состояния: `uploaded`, `needs_mapping`, `queued`, `validating`, `importing`, `calculating`, `ready`, `failed`, `cancelled`.

Невалидное сопоставление возвращает импорт в `needs_mapping`. После выбора схемы обработка идёт в фоне. Длинные операции не выполнять внутри HTTP-запроса.

Версия 1.0 допускает безопасный перезапуск текущего этапа с начала вместо сложного возобновления с произвольного байта. Уже завершённые этапы повторно использовать, если их входные данные и версии правил не изменились. Каждый этап идемпотентен; повторный запуск не создаёт двойные наблюдения.

Одновременно разрешён один тяжёлый импорт. Обработчики импортов и интерактивных экспортов используют разные очереди и worker-процессы. Таймаут задания должен быть меньше `retry_after`; зависшие задания обнаруживаются по heartbeat и переводятся в восстанавливаемое состояние.

Отмена проверяется между пакетами. Неопубликованные данные не видны в поиске. После ошибки приложение сохраняет рабочий предыдущий отчёт и даёт понятную причину сбоя.

## 7. Метрики и приоритизация

Все расчёты реализуются в backend и переиспользуются UI, REST и MCP. Формулы версионируются. Frontend форматирует числа, но не пересчитывает бизнес-метрики независимо.

### 7.1. Базовые определения

Пусть `f1 … fn` — точные частотности от старого к новому внутри выбранного диапазона одного отчёта.

| Метрика | Определение |
|---|---|
| Текущая частотность | `fn`; не подменять последним непустым значением |
| Абсолютное изменение | `fn − f1`, если обе границы известны |
| Относительное изменение | `(fn − f1) / f1`, если `f1 > 0` |
| Изменение ранга | `rank_previous − rank_current`, если предыдущий ранг больше нуля |
| Низкая база | Базовое значение меньше 20 по умолчанию; порог настраивается |
| Признак появления | Предыдущий ранг равен нулю; отдельный признак от роста частотности |
| Широкая / точная | Отношение широкого к точному для одного замера; при нулевой точной — `NULL` |

Для `f1=0, fn>0` процент роста равен `NULL`, причина `zero_baseline`; показывать «рост от нуля» и абсолютное изменение. Для `0→0` процент также не определён. Не использовать скрытую прибавку единицы к знаменателю.

### 7.2. Сглаженный рост и устойчивость

Метрики ниже считать для полного ряда из минимум четырёх выбранных замеров, без пропусков:

```text
B = (f1 + f2) / 2
R = (f[n−1] + fn) / 2
A = R − B
G = (R − B) / B                  при B > 0
C = число переходов f[i] > f[i−1] / (n−1)
P = fn / max(f1 … fn)            при максимуме > 0
```

`B` — ранняя база, `R` — поздний уровень, `A` — сглаженный абсолютный прирост, `G` — сглаженный относительный рост, `C` — доля положительных переходов, `P` — сохранение спроса относительно наблюдаемого пика. Равные значения не считаются положительным переходом.

При неполном ряде эти метрики не заменять оценками по выборочным точкам; возвращать `NULL` и причину. Сравнение двух известных границ остаётся доступным отдельно.

Стартовый пресет «Устойчивый рост»:

- минимум четыре полных замера;
- `fn >= 100`;
- `B >= 20`;
- `A >= 50`;
- `G >= 0.30`;
- `C >= 0.60`;
- `P >= 0.70`.

Все пороги доступны в настройках пресета. Это рабочие эвристики для первичного отбора, а не статистически валидированные границы перспективности. Предусмотреть отдельные пресеты «Ранние сигналы» и «Рост от нуля», где результаты не смешиваются с основным рейтингом.

Стартовые условия «Ранних сигналов»: минимум четыре полных замера, `0 < B < 20`, `fn >= 50`, `A >= 30`, `G >= 1`, `C >= 0.60`, `P >= 0.70`; сортировка по `A` убыванию. Для «Роста от нуля»: минимум четыре полных замера, `B=0`, `fn >= 50`, `A >= 30`, `P >= 0.70`; сортировка по `A` убыванию. В обоих случаях основной приоритет не показывать; явно объяснять меньшую надёжность сигнала.

### 7.3. Признаки задачи для онлайн-сервиса

Создать редактируемые правила на токенах, фразах и комбинациях слов. Примеры категорий: конвертация, расчёт, генерация, обработка файлов, мониторинг, сравнение, учёт, автоматизация.

Пример положительного правила: наличие «конвертер», «рассчитать», «автоматизировать», «генератор» или комбинации «из pdf в …». Пример слабого сигнала: одиночное «онлайн», которое встречается и в развлекательных запросах.

Каждое правило содержит ID, категорию, условие, вес `0…1`, пояснение и версию. Итог `T` равен максимальному весу сработавшего положительного правила; без совпадений `T=0`. Исключения брендов и нерелевантных тем применяются отдельными фильтрами, не скрытым штрафом.

Теги считаются эвристическими и могут исправляться вручную. Веса и начальный словарь поставляются в репозитории, проверяются на демонстрационных примерах. Не требуется отправлять миллионы фраз в LLM.

### 7.4. Приоритет исследования, версия `priority_v1`

Для полного ряда при `B>=20`:

```text
clip(x) = min(1, max(0, x))
g = clip(G / 2)
a = clip(ln(1 + max(A, 0)) / ln(10001))
v = clip(ln(1 + fn) / ln(100001))
priority = round(100 × (0.30g + 0.25a + 0.20C + 0.15v + 0.10T))
```

Для ранжирования кандидатов сначала применяется выбранный пресет, затем `priority`. Значения приоритета для низкой базы, пропусков или недостатка истории — `NULL`, с причиной. Для произвольной выборки вычисление допустимо, но наличие числа не означает прохождение пресета.

Компоненты и вклад каждого доступны в UI/API. Фиксированные масштабы нормализации обеспечивают воспроизводимость между импортами; значения `2`, `10000`, `100000` — стартовые настройки профиля. При их изменении создаётся новая версия профиля и пересчёт, прежние результаты сохраняются.

Название в интерфейсе — «Приоритет исследования», не «вероятность успеха» и не «оценка прибыльности». Данных о конкуренции в эту формулу не включать.

### 7.5. Метрики ниши и сравнение отчётов

Внутри отчёта зафиксировать состав ниши `K`. Для общей динамики взять подмножество `K_complete`, у которого известны все выбранные точные частотности. Для каждого замера суммировать значения одного и того же `K_complete`. Показывать размер полного состава, размер пригодного подмножества и процент покрытия. Если подмножество пусто, график и рост недоступны.

Дополнительно показывать:

- долю участников `K_complete` с положительным сглаженным приростом;
- долю крупнейшей фразы в текущей сумме; при нулевой сумме — `NULL`;
- медиану сглаженного относительного роста только для участников с положительной базой и число таких участников;
- список лидеров вклада в абсолютное изменение;
- число исключённых из динамики фраз из-за неполной истории.

Скалярный приоритет ниши в версии 1.0 не требуется: сравнивать ниши по нескольким показателям и подтверждающим фразам.

При сравнении двух отчётов пользователь явно выбирает базовый и текущий. Сравниваются их текущие замеры, только при совпадении региона и определения частотности. При неизвестном периоде показать соответствующую отметку. Рост суммы считать на пересечении фраз, имеющих значения в обоих отчётах. Вошедшие и отсутствующие фразы показывать отдельно; отсутствие не заменять нулём. Для сохранённой ниши дополнительно фиксировать версию её состава. Изменение состава двух топов не должно выглядеть как рост всей темы.

### 7.6. Автоматические предложения групп

После расчёта метрик сформировать исходный набор фраз, проходящих пресет «Устойчивый рост». По умолчанию использовать до 100 000 лидеров по приоритету, с детерминированным вторичным ключом. В метаданных сохранять фактический размер и факт ограничения.

Построить группы по одиночным токенам и соседним парам токенов после исключения редактируемого списка стоп-слов. Минимум пять разных фраз в группе. Учитывать каждую фразу один раз внутри группы. Группы с одинаковым составом схлопывать детерминированно. В версии 1.0 не требуется сложное объединение частично пересекающихся групп.

Метрики предложения считаются только по его фактическим участникам. Показывать «группа по словам из отобранных растущих фраз» и охват исходного набора. Действие «Расширить» запускает поиск по всему отчёту, включая нерастущие фразы; перед сохранением ниши пользователь проверяет полный состав. Это отделяет удобный способ обнаружения темы от оценки всей доступной темы.

## 8. Модель данных

Физические типы и индексы уточняются при реализации, семантика сущностей обязательна.

| Сущность | Основные поля и ограничения |
|---|---|
| `source_files` | UUID, имя, SHA-256 unique, размер, путь, время загрузки |

| `dataset_keywords` | dataset_id, keyword_id, source row, текущий/предыдущий ранг, исходные длины; unique(dataset_id, keyword_id) |
| `observations` | scan_id, keyword_id, exact bigint nullable, broad bigint nullable; unique(scan_id, keyword_id), значения >=0 |
| `metric_runs` | UUID, dataset_id, диапазон замеров, версия алгоритма, настройки профиля, версия правил, статус |
| `keyword_metrics` | metric_run_id, keyword_id, текущие значения, B/R/A/G/C/P/T, priority, quality flags; unique(run, keyword) |

| `niches` | UUID, название, описание, тип fixed/rule, правило выбора, ручные включения/исключения |
| `niche_versions` | UUID, niche_id, dataset_id, metric_run_id, версия состава, created_at, агрегаты, coverage |
| `niche_members` | niche_version_id, keyword_id; unique(version, keyword) |
| `hypotheses` | UUID, niche_id, поля из раздела 5.6, status, timestamps |
| `hypothesis_evidence` | hypothesis_id, keyword_id, dataset_id, metric_run_id/niche_version_id, сохранённые значения |
| `import_jobs`, `export_jobs` | статус, параметры, прогресс, attempts, heartbeat, error, result_path, timestamps |
| `import_errors` | import_job_id, номер записи, колонка, код, сообщение |

Метрики материализуются для полного диапазона отчёта и профиля по умолчанию. Произвольный диапазон или изменение профиля создаёт фоновый `metric_run`; результаты не пересчитываются синхронно для миллионов строк на каждое движение фильтра. Готовые расчёты повторно используются по хешу параметров.

Для трёх миллионов фраз в подтверждённом формате с шестью замерами возможно до 18 млн наблюдений на один отчёт. Каждое наблюдение хранит обе частотности. Число замеров не зашивать в код; контроль расширяемости с семью замерами даёт до 21 млн наблюдений. Планирование диска и производительности должно учитывать наблюдения и индексы, а не только строки CSV. Сохранять несколько отчётов разрешено; в v1 не требуется физически дедуплицировать одинаковую историю разных файлов.

Обязательные индексы: принадлежность фраз отчёту, чтение истории по keyword_id/scan_id, сортировка метрик внутри metric_run, поиск по search_text. `pg_trgm` поддерживает индексированный поиск `LIKE`/`ILIKE` и похожих строк; короткие и неселективные шаблоны требуют отдельных замеров производительности. [Документация pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html).

Кешировать результаты по dataset_id, metric_run_id, версии правил и каноническому JSON фильтров. Переключение активного отчёта не должно смешивать кеши. В v1 кеш допустимо хранить в PostgreSQL.

Удаление отчёта требует подтверждения. При наличии ссылок из гипотез/ниш показывать зависимости и блокировать физическое удаление до их удаления или переноса. Смена активного отчёта и архивирование не удаляют историю.

## 9. REST API

Префикс `/api/v1`. JSON, OpenAPI-описание, единая схема фильтров для UI и MCP. Локальное приложение без аутентификации: все маршруты REST, включая мутации, доступны без входа и токенов (доступ ограничен loopback-портом Docker-хоста).

| Метод и путь | Назначение |
|---|---|
| `POST /datasets` | Загрузить CSV; вернуть ID и статус, без ожидания импорта |
| `GET /datasets`, `GET /datasets/{id}` | Список, метаданные, схема и качество |
| `PUT /datasets/{id}/mapping` | Сопоставление колонок и замеров до обработки |
| `POST /datasets/{id}/import` | Поставить импорт в очередь |
| `POST /imports/{id}/cancel`, `/retry` | Отмена и повтор |
| `GET /imports/{id}` | Прогресс и ошибки |
| `POST /metric-runs` | Запросить расчёт диапазона и профиля |
| `GET /metric-runs/{id}` | Статус или ссылка на готовые метрики |
| `POST /keywords/search` | Поиск, фильтрация и курсорная пагинация |
| `GET /keywords/{id}/history?dataset_id=…` | Наблюдения и метаданные замеров |
| `POST /analytics/summary` | Агрегаты выбранной выборки |
| `POST /analytics/compare` | Сравнение двух отчётов с описанием состава |
| `GET /candidate-groups?metric_run_id=…` | Предложения групп и охват |
| CRUD `/saved-searches`, `/niches`, `/hypotheses` | Управление собственными сущностями |
| `POST /niches/{id}/evaluate` | Создать новую версию состава и оценки |
| `POST /exports` | Поставить экспорт в очередь |
| `GET /exports/{id}`, `GET /exports/{id}/download` | Статус и скачивание |

CRUD означает стандартные `GET` коллекции/ресурса, `POST`, `PATCH`, `DELETE`. Активацию и архивирование отчёта реализовать через `PATCH /datasets/{id}`; физическое удаление — через `DELETE /datasets/{id}` с проверкой зависимостей.

Пример поискового запроса:

```json
{
  "dataset_id": "<dataset UUID>",
  "metric_run_id": "<готовый metric run UUID>",
  "filters": {
    "include": {"terms": ["конвертер", "генератор"], "mode": "any", "match": "token"},
    "exclude": {"terms": ["игра"], "match": "token"},
    "exact_current": {"min": 100},
    "smoothed_growth": {"min": 0.30},
    "smoothed_delta": {"min": 50},
    "consistency": {"min": 0.60},
    "history_complete": true
  },
  "sort": [{"field": "priority", "direction": "desc"}],
  "limit": 50,
  "cursor": null
}
```

Ответ содержит `data`, `next_cursor`, `truncated`, `dataset_id`, `metric_run_id`, `algorithm_version`, фактически применённые фильтры и предупреждения. `truncated` означает наличие невыданных совпадений; `next_cursor` позволяет продолжить, если действует только пагинация. Жёсткое ограничение объёма дополнительно обозначается `hard_limit_reached`. Точное `total_count` необязательно; если не вычислено, возвращать `null`, а не оценку без подписи.

Для метрик возвращать значения и `null_reasons`; для агрегатов — охват и число исключённых фраз. Ошибка: `code`, `message`, `details`, `request_id`. Примеры кодов: `DATASET_NOT_READY`, `INSUFFICIENT_HISTORY`, `INCOMPATIBLE_MEASUREMENTS`, `QUERY_TOO_BROAD`.

Тяжёлые агрегаты могут вернуть `202` с `job_id`; `GET /jobs/{id}` возвращает статус и результат. Общий механизм заданий используется API и MCP. Валидировать поля сортировки и фильтров по разрешённому списку; SQL из клиента не принимать.

## 10. MCP для внешнего ИИ-агента

Реализовать через `laravel/mcp`, который предоставляет инструменты, ресурсы и локальные серверы через Artisan. [Документация Laravel MCP](https://laravel.com/docs/13.x/mcp).

Обязательный транспорт — stdio для локального агента. Пример запуска после регистрации сервера `niche-radar`:

```bash
docker compose exec -T app php artisan mcp:start niche-radar
```

Предоставить JSON-пример конфигурации MCP-клиента с командой, аргументами и рабочей директорией проекта. Для удалённого облачного клиента localhost/stdio недостаточно; HTTP-доступ, OAuth и публичный адрес не входят в v1. Отдельно задокументировать это ограничение.

| Инструмент | Результат |
|---|---|
| `list_datasets` | Доступные отчёты и их состояние |
| `get_dataset_schema` | Замеры, даты, определения полей и предупреждения |
| `search_keywords` | Фразы и метрики по структурированным фильтрам |
| `get_keyword_history` | Полная доступная история одной фразы в отчёте |
| `summarize_selection` | Агрегаты, охват и состав выборки |
| `compare_datasets` | Динамика общей части и отдельные списки входа/выхода |
| `list_candidate_groups` | Группы-кандидаты с методом получения |
| `list_niches`, `get_niche` | Сохранённые ниши и выбранная версия оценки |
| `list_hypotheses`, `get_hypothesis` | Сохранённые гипотезы и доказательства |
| `get_job_status` | Результат отложенного аналитического запроса |

Инструменты read-only: импорт, удаление, редактирование и запуск произвольного SQL через MCP запрещены. Фоновый расчёт агрегата допустим как техническое кеширование без изменения пользовательских сущностей. Для неподготовленного диапазона вернуть требование создать metric_run через UI/API.

В каждом инструменте обязательны JSON Schema входа/выхода, описание единиц, правила пропусков и ограничения. По умолчанию выдавать 50 строк, максимум 200; ограничить размер сериализованного ответа 256 KiB с явным `truncated`. После отсечения по размеру курсор должен продолжать с первой невыданной строки.

Ресурс `niche-radar://methodology` описывает формулы, версии и ограничения источника. Числа всегда получаются из backend; агент не должен самостоятельно угадывать значения. Текст поисковых фраз возвращается как данные, не как инструкции для агента.

Приёмочный сценарий: агент получает схему отчёта, находит растущие запросы по конвертации файлов, исследует историю пяти лидеров и выдаёт кандидатов с ID фраз, значениями и ограничениями данных. Наличие оплаченного LLM не требуется для технической проверки MCP: достаточно протокольного клиента.

## 11. Экспорт

- CSV текущей отфильтрованной выборки: исходная фраза, метрики, флаги, ID отчёта и версии расчёта.
- CSV состава и оценки ниши.
- Markdown карточки гипотезы с доказательствами, параметрами выборки и датой экспорта.
- Полные выгрузки создавать потоково в фоне; не ограничивать их размер лимитом строки таблицы UI.
- По умолчанию CSV UTF-8 с BOM, разделитель `;`, корректное экранирование кавычек.
- Предусмотреть «для таблиц» с защитой текстовых ячеек от формул и «исходные значения» для программной обработки. В первом режиме значения, начинающиеся с потенциальных префиксов формулы, экранировать; не менять оригинал в БД.
- Файл доступен только владельцу. Временные экспорты удаляются через 7 дней по умолчанию; оригиналы и гипотезы автоматически не удаляются.

## 12. Docker Compose и эксплуатация

### 12.1. Контейнеры

| Сервис | Назначение |
|---|---|
| `web` | Nginx, React static, проксирование PHP; порт по умолчанию `127.0.0.1:8080` |
| `app` | PHP-FPM, Laravel API и CLI; общий образ с worker |
| `worker-import` | Импорт и тяжёлые расчёты, concurrency=1 |
| `worker-default` | Экспорты и интерактивные фоновые агрегаты, concurrency=1 |
| `scheduler` | Очистка экспортов, поиск зависших задач, обслуживание |
| `db` | PostgreSQL; порт не публикуется наружу |
| `migrate` | Однократные миграции и идемпотентная инициализация перед запуском приложения |

React собирается в multi-stage Docker build. Node.js нужен на этапе сборки, отдельный production Node.js-контейнер не требуется. Redis, Elasticsearch, ClickHouse и отдельный MCP-сервис не входят в базовый Compose.

Volumes: `postgres_data`, `app_storage` с подпапками originals/staging/exports. `app`, workers и scheduler используют один storage volume; доступ Nginx к приватным исходникам запрещён. Завершение контейнеров не удаляет данные.

### 12.2. Запуск

Поставить `.env.example`, скрипт `./bin/setup` и инструкции:

```bash
./bin/setup
docker compose up -d --build
```

`setup` выполняется без установленных на хосте PHP, Node.js или PostgreSQL: создаёт `.env`, генерирует APP_KEY и пароль БД. Не перезаписывает уже заданные значения. Не фиксировать стандартный пароль в репозитории. Файл `.env` исключён из git.

После `up` приложение должно открываться на `http://localhost:8080`. `migrate` ждёт готовности PostgreSQL и завершается успешно до старта app/workers; миграции не запускаются конкурентно из каждого контейнера. Использовать healthcheck и условия `service_healthy`/`service_completed_successfully`: порядок запуска контейнеров сам по себе не гарантирует готовность зависимостей. [Документация Docker Compose](https://docs.docker.com/compose/how-tos/startup-order/).

Заполнение стартовых наборов правил идемпотентно: повторный запуск не дублирует и не изменяет пользовательские данные. Перезапуски не создают демонстрационные записи в рабочей БД.

Обязательные команды проекта:

| Команда | Результат |
|---|---|
| `./bin/import /absolute/path/report.csv` | Передать локальный файл обработчику без ограничений HTTP-загрузки; создать тот же импорт, что в UI |
| `./bin/backup /absolute/path/backup-dir` | Согласованная резервная копия БД, оригиналов и необходимых метаданных |
| `./bin/restore /absolute/path/backup-dir` | Восстановление с подтверждением замены существующих данных |
| `./bin/test` | Запуск обязательных тестов в Docker |
| `./bin/benchmark` | Воспроизводимый генератор/прогон контрольной нагрузки и отчёт |

На время backup/restore останавливать мутации и фоновые записи либо обеспечивать согласованный снимок другим документированным способом. Копия должна включать гипотезы, ниши, конфигурации и данные для восстановления файловых ссылок. Секреты восстанавливаются отдельно по инструкции; сохранение APP_KEY необходимо, если имеются зашифрованные данные.

### 12.3. Доступ и диагностика

Аутентификации нет: приложение личное и локальное, UI и REST работают без входа, сессий и токенов; доступ ограничен loopback-портом Docker-хоста. Локальный stdio MCP запускается с доверием к владельцу Docker-хоста и ограничивается read-only инструментами.

Логи: request_id/job_id, этапы, длительность и ошибки без секретов. Health endpoints различают доступность процесса и готовность БД; состояние worker отражается heartbeat. Для удалённого размещения владелец отдельно настраивает TLS и доступ; базовая поставка слушает loopback.

## 13. Производительность и объём

Контрольная среда: Linux, 4 vCPU, 16 GiB RAM, SSD; 100 GiB свободного диска — стартовый резерв для проверки, не гарантия вместимости любого числа отчётов. До импорта показывать размер исходника и доступное место; фактический коэффициент расширения измерить на первом полном отчёте.

Основной контрольный набор: 3 млн уникальных фраз и шесть пар частотностей по схеме `Top10.csv`; дополнительно проверить, что седьмой замер поддерживается без изменения кода. Полный реальный CSV обязателен для итогового профилирования; до его получения использовать воспроизводимый генератор с реалистичным распределением длины строк, частотностей и общих токенов. Десяти строк недостаточно для подтверждения производительности или распределений полного набора.

Целевые бюджеты, подлежащие проверке, а не обещанные заранее результаты:

| Операция | Цель |
|---|---|
| Импорт и подготовка стандартного профиля | До 30 минут на контрольном наборе, без времени передачи файла |
| Память процесса импорта | До 1 GiB RSS; не растёт линейно с размером CSV |
| Первая страница селективного поиска, до 1% строк | p95 ≤ 1,5 с при прогретой БД и без импорта |
| Страница по предрассчитанному приоритету | p95 ≤ 1 с |
| История одной фразы | p95 ≤ 500 мс |
| Готовая сводка ниши | p95 ≤ 1 с |
| Широкий агрегат по всему набору | До 10 с синхронно, далее асинхронный job |
| Ответ UI на старт задания | До 1 с после приёма файла/параметров |

Бенчмарк фиксирует версии, ресурсы Docker, объём БД и индексов, параметры запросов, холодный/прогретый режим и число повторов. Минимум 30 повторов для измеряемой категории; результаты p50/p95. Во время импорта отдельно проверить сохранение доступности активного отчёта, без требования тех же latency.

При превышении бюджета сначала исследовать планы SQL, индексы, материализацию и размер пакетов. Изменение архитектуры или бюджета фиксируется отдельно по результатам измерений. Нельзя объявлять соответствие без полного прогона.

### 14.1. Корректность данных и аналитики

| Предыдущий ранг `0` | «Впервые в рейтинге», без фиктивного rank_delta |

| Ряд `[100, 120, 150, 180]`, T=0 | Приоритет по priority_v1 равен 45 после округления |
| Ряд `[100, 100, 100, 100]` | A=0, G=0, C=0; не проходит устойчивый рост |
| Ряд `[100, 100, 1000, 110]` | P=0,11; не проходит основной пресет |
| Ряд `[0, 0, 100, 200]` | G и основной приоритет NULL; метка роста от нуля |

| Одинаковая фраза в двух нишах | При объединённой сводке учитывается один раз |

### 14.2. Работа приложения

- На чистом Docker-хосте приложение запускается указанными командами, без локальной установки языка и БД.
- Импорт контрольного набора доходит до `ready`; UI, API и MCP возвращают согласованные значения для одной версии расчёта.
- Двойная загрузка одинакового файла не удваивает данные.
- Прерывание worker во время импорта и повторный запуск не создают частично опубликованный отчёт или дубликаты.
- Перезапуск Compose сохраняет активный отчёт, ниши, гипотезы и параметры.
- Сохранённый поиск восстанавливает все условия и сортировку; `latest` фиксируется в конкретный dataset_id при выполнении и в экспортируемых результатах.
- Пагинация не пропускает и не повторяет строки при одинаковых значениях сортировки в неизменяемом metric_run.
- Экспорт соответствует всей выборке, а не текущей странице; поля и формат чисел документированы.
- REST отвечает без аутентификации (локальный loopback-доступ), включая мутации.
- MCP корректно отвечает на initialize/tools/list/tools/call; stdout не содержит логов приложения, только протокольные сообщения.
- Backup восстанавливается в пустые volumes и возвращает те же контрольные значения и гипотезы.
- Выполнен бенчмарк из раздела 13; его результаты приложены к поставке.

Обязательные тесты: unit для формул и правил пропусков; интеграционные для импорта, повторных запусков, фильтров и общей логики REST/MCP; один E2E-сценарий «импорт → фильтры → ниша → гипотеза → экспорт». Предпочитать тесты, выявляющие ошибки данных, а не проверки внутренней структуры классов.

| 4. Рабочие гипотезы | Карточки гипотез, доказательства, сравнение отчётов и версий ниш |
| 5. Интеграции и завершение | OpenAPI, read-only MCP, восстановление из backup, E2E и итоговый бенчмарк |

Первый полезный результат достигается после этапа 2: исследование реального отчёта через фильтры. Версия 1.0 считается завершённой после этапа 5 и прохождения критериев приёмки.

Перед реализацией не требуется выбирать между тремя backend-стеками: в данном ТЗ принят Laravel. Реальный образец уже позволяет реализовать и проверить распознавание формата, порядок колонок, дубликаты текущего замера и контрольные значения. Для окончательной проверки качества всего набора и производительности нужен полный CSV. Неизвестные даты не блокируют работу с порядковой историей, но ограничивают календарную интерпретацию динамики.
